# 上下文工程 — 渐进压缩、磁盘卸载、摘要与预算

Kin 目前把上下文管理交给 Claude Agent SDK。这很方便，但意味着当长对话、大工具输出或大量检索结果接近上下文限制时，Kin 没有明确策略。本课描述 Kin 尚未实现的一个显式上下文工程层设计。

## 状态

仅设计，未实现。

## 问题

长对话和大工具输出（例如匹配一万行的 `grep` 或 50 KB 文件）会快速消耗上下文窗口。系统必须在预算内保留最相关信息，同时不丢失引用、不淹没模型。困难在于压缩步骤本身也不能把预算推过限制。

## 为什么朴素方案失败

- **单阈值截断**：到达限制时砍掉最旧消息，会丢弃早期但仍然关键的信息。
- **完全依赖 SDK autocompact**：SDK 不知道 Kin 的业务语义（哪些消息是检索结果、哪些引用必须保留、哪些输出可以卸载）。
- **全部摘要**：摘要有损且消耗 token，可能反而恶化预算问题。

## 设计

> **以卸载优先的渐进压缩。在调用 `query()` 前估计 token 预算，然后应用轻量压缩、附件卸载，最后必要时才用 LLM 摘要较旧轮次。**

- **调用前预算**：在下次 `query()` 调用前估计 token 使用。这防止压缩步骤本身超过窗口。
- **卸载 > 摘要**：大工具输出写入 `message_attachment`（该表已存在），只在上下文中保留一个短前缀加附件指针。把数据移出上下文比摘要更便宜且更少损失。
- **渐进层级**：先应用轻量压缩（去重、尾部截断），然后卸载大块，最后才用便宜模型摘要较旧轮次。
- **与 RAG 和记忆集成**：检索结果按需加载，重复检索结果被压缩，检索历史反馈进记忆以避免重复搜索。

## 反直觉结论

> **最好的上下文压缩不是摘要，而是卸载加指针。**

摘要有损且费 token。把大工具输出卸载到 `message_attachment` 并在上下文只保留指针，几乎免费且保留完整文本。Kin 幸运的是 `message_attachment` 表已经存在；缺失的是把它接入上下文管线。

## 生产坑

- **压缩必须在 LLM 调用前决定**，而不是调用过程中。
- **流式缓冲不能持有大量未卸载输出**。先把输出写入磁盘，再在上下文中包含指针。
- **如果 SDK autocompact 仍启用，边界必须清晰**，以免 Kin 的显式压缩与 SDK 内部压缩互相冲突。
