# 评估 — 黄金集、检索/生成指标、离线 + 在线与回归门

评估最初只是设计阶段的能力。构建 RAG 迫使它变成现实。本课描述已存在的检索评估、尚未实现的生成评估，以及评估如何改变了一个具体设计决策。

## 状态

检索评估：已实现。生成评估与 CI 回归门：尚未实现。

## 问题

chunking、embedding、rerank 或 prompt 的任何改动都可能让系统更好或更坏。没有可重复指标，优化就是猜测，回归也无法察觉。

## 为什么朴素方案失败

- **人工抽查**：漏掉回归，无法规模化。
- **只在线反馈**：太慢太晚；无法在坏合并到达用户前阻止它。
- **只端到端测试**：坏答案可能由检索、rerank 或生成导致。只测最终答案掩盖了失败位置。

## 设计

> **每个知识库维护精选黄金集，按检索腿类型拆分，使用分层检索与生成指标，离线运行 CI 回归门，并辅以在线信号。**

- **黄金集**：维护一组问题、期望相关 chunk 和期望答案。问题应按所锻炼的检索技能分类：关键词、改写、实体、条款。
- **分层指标**：检索指标（Recall@K、MRR、NDCG）和生成指标（忠实度、答案相关性、引用正确性）。
- **离线 CI**：每次合并运行评估作为回归门。关键指标低于阈值则阻塞合并。
- **在线**：从 `usage_record` 和 `audit_log` 采样使用和反馈，捕捉长尾问题。

## 实际落地了什么

检索评估层与 RAG 一起构建，并驱动了一个重大设计反转。

- **按检索腿类型分类的黄金集**：`tests/golden/rag-golden-set.ts` 包含按关键词、改写、实体、条款分类的问题。这防止单一类别（如改写）让某个检索腿看起来没用。
- **消融模式**：`scripts/rag-eval-v2.ts` 报告 `R@1`、`R@4`、`R@8` 和 MRR，并在三种模式下运行：纯向量、混合、混合+rerank。这隔离每个腿的贡献。
- **Rerank 默认关闭**：评估显示在生产 `k=8` 时，rerank 没有提升 `R@8`。模型会读全部 8 个 passages，rerank 只改变顺序而不提升召回，同时每查询增加约 1.4 秒。Rerank 现在由 `RAG_RERANK_ENABLED` 控制，默认 false。

## 仍然缺失什么

- **生成指标**：忠实度、答案相关性、LLM-as-judge 评分尚未实现。
- **CI 回归门**：`scripts/rag-eval-v2.ts` 目前手动运行。尚未接入 `.github/workflows`。

## 反直觉结论

> **评估不是功能后清单；而是优化的先决条件。**

没有可重复指标，任何设计改动都无法证明更好或更坏。评估的价值不仅在于证明方法有效，还在于在方法被固化进生产前发现它无效。rerank 反转就是典型例子。

## 生产坑

- **黄金集会过期**。知识库变化时更新它们。
- **LLM-as-judge 有方差**。固定 judge 模型并多采样平均。
- **端到端测试掩盖分层失败**。分别报告检索和生成指标。
