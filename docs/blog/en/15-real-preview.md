# Real Preview — running AI-generated multi-file apps in per-session Docker

A serious AI workspace must run the code it generates, not just display it. Kin's preview is not an iframe overlay or a browser sandbox. It is a real, per-session Docker environment that installs dependencies, builds the project, and serves the result behind a subdomain with authentication. This lesson explains the four-stage pipeline and the trade-offs involved in hosting untrusted, generated code on the same machine as the main application.

## The problem

A real preview must satisfy four competing requirements at once:

1. **Multi-file, real builds**: AI output is often a complete Vite/React project with `package.json` and `src/**`. It needs real `npm install` and `npm run build` to surface real build errors, real dependencies, and real routing.
2. **Bounded resources**: 50 active sessions cannot each keep a Node dev server running; that would OOM a 16 GB host.
3. **Security**: the code is generated by a user through the model. It must not read other users' files, exfiltrate secrets, or act as an internal network pivot.
4. **Browser embeddability**: the preview must be visible in an iframe inside the chat UI, so it needs a public URL, authentication, and working HMR websocket.

Rendering generated output is not a frontend problem; it is a miniature PaaS problem.

## Why the naive options fail

- **Sandpack / WebContainers**: browser-based sandboxes cannot run real `npm install` with arbitrary dependencies, cannot surface real build errors, and cannot run Node-only backend code. They are useful for demos but insufficient for real engineering output.
- **One dev server per artifact**: keeping a live dev server per artifact consumes memory proportional to the product of sessions and artifacts. This quickly exceeds the host budget.
- **Subpath reverse proxy (`/preview/<id>/...`)**: Vite HMR and relative imports break when the base path is rewritten. A first-level subdomain is required.
- **Dynamic Let's Encrypt certificates per preview**: Cloudflare free tier only covers one wildcard level, and Full(Strict) mode blocks HTTP-01 validation. Dynamic issuance is impractical in this deployment shape.

## The core design

> **Per-session persistent Docker (not per-message, not per-artifact) + build-first static hosting + Traefik subdomain proxy + Cloudflare Origin CA + bootstrap JWT → cookie authentication + idle reaper.**

```
① Detection & manifest    ② Build & host            ③ Proxy & expose       ④ Auth & embed
manifest.js                 preview controller         Traefik                auth.js
scan package.json           (only Docker socket)      *.oxygenie.cc          /preview?t=<JWT 90s>
→ .oxygenie/app.json        per-session container     HostRegexp routing     → /__oxy/auth
install/build/dev/port      install→build→serve      Origin CA cert         → oxy_preview cookie
entryFiles                  idle 5–10 min reclaim     dynamic labels         → iframe sandbox
                            MAX_ACTIVE_PREVIEWS=4
```

- **Manifest detection**: heuristic scan of the project to identify framework, entry points, and port, producing `.oxygenie/app.json`. Only declared `package.json` scripts are executed; no free shell is given to the model.
- **Build and hosting**: a per-session Docker container persists across messages to keep a warm `node_modules` cache. The pipeline is build-first, with dev/HMR as best-effort. `MAX_ACTIVE_PREVIEWS=4` and idle timeout keep resource usage bounded.
- **Proxy exposure**: each preview gets `<previewId>.oxygenie.cc` via Traefik `HostRegexp`. A single Cloudflare Origin CA certificate is issued once and reused for all routes, bypassing the dynamic-issuance problem.
- **Authentication**: a 60–120 second bootstrap JWT is exchanged for a 10–15 minute `httpOnly` opaque `oxy_preview` cookie on first access. The iframe uses `sandbox="allow-scripts allow-forms allow-downloads"` without `allow-same-origin`, providing origin isolation from the main site.

## Status: delivered, with one remaining architectural tension

Phase C (real preview) has been delivered and is live. The preview pipeline is functional, including build-first static serve, Traefik subdomain routing, Origin CA certificates, and JWT/cookie authentication.

What remains is a **runtime architecture tension**: the agent executes in a per-message worker, while the preview runs in a per-session container. These are two different lifecycles that currently share the same workspace but are not unified. If the agent writes a file, the preview container must see it, and vice versa. The shared workspace is the coupling point. Unifying the two runtimes — either by warming a shared workspace pool or by collapsing the distinction — is a long-term architectural debt, not a functional bug.

## The counter-intuitive conclusion

> **Rendering an AI-generated app is not a frontend problem; it is a miniature PaaS problem.**

The real engineering is in Docker lifecycle, Traefik routing, certificate management, cookie authentication, and idle reclamation. The iframe is the last 1%. The preview system also reuses Kin's existing isolation philosophy: bounded concurrency, process/container boundaries, and build-first stateless execution.

## Production pitfalls

- **Traefik v3 `HostRegexp` syntax and YAML escaping are unforgiving**. A single escaping error produces a silent 404. Test with a fixed subdomain before enabling the wildcard pattern.
- **Agent and preview runtimes are not unified**. Be aware that workspace files must be visible to both the per-message worker and the per-session preview container.
- **The structured-output path to artifact detection is currently off by default**. The stop-hook for SDK `outputFormat` leaks internal instructions into the conversation context, so artifact detection remains heuristic, with `.oxygenie/app.json` as the stable ground truth.
